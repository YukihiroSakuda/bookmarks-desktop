## Product Overview

### Vision

作業の開始だけでなく**終了**まで扱う。ブラウザのタブとローカルのフォルダを1つの「作業セッション」として、丸ごと開き、丸ごと畳む。

### Problem Statement

#### 前提: グループ機能だけでは差別化にならない

002 で実装したグループ（ワンクリック一括起動）は、**ブラウザの世界ではすでに一般的**である。Toby、Workona、ブラウザ標準のタブグループがいずれも「タブ一式をワンクリックで開く」を提供している。この軸で競合と戦っても勝てない。

差別化しているのは**ローカルパス側の半分**である。

| ツール | URL | ローカルパス | ブラウザの外から使えるか |
|--------|-----|------------|--------------------|
| ブラウザ標準 / Toby / Workona | ○ | × | × |
| Raindrop / Pocket | ○ | × | △ |
| Everything / Listary | × | ○ | ○ |
| **本アプリ** | **○** | **○** | **○** |

本アプリは `kind = 'url'` と `kind = 'path'` を同じオブジェクトとして扱い、かつ Windows シェルの中に住んでいる（Explorer 右クリック、`.lnk` ミラー、Quick Access、トレイ、グローバルホットキー）。**この2つを同時に満たすツールが存在しない。**

#### 残っている問題

1. **グループを手で組み立てるコストが高い** — 002 の Groups ビューは検索欄からの追加を速くしたが、**そもそも「何を入れるべきか」を人間が思い出す必要がある**。実際にはその答えは画面上にすでに開いている。作業中のブラウザのタブと Explorer のウィンドウが、そのまま作業セットである
2. **「作業を終える」瞬間に何もない** — どのツールも「始める」しか作っていない。案件Aを終えて案件Bに移るとき、開いたタブとウィンドウを1つずつ閉じる作業が残る。閉じ忘れれば次の作業に前の作業のノイズが混ざる
3. **作業の中断と再開が繋がらない** — 昨日どこまでやったかは、開いていたものの集合に表れているのに、それを保存する手段がない

### Value Proposition

- **最初のグループがタダで手に入る** — 手で組み立てる代わりに、今開いているものをそのまま保存する
- **ブラウザと Explorer をまたいで掴める** — Toby も「今のタブを保存」はできるが、ブラウザの中からしか見えないのでタブしか保存できない。ネイティブアプリとブラウザ拡張の両方を持つ本アプリだけが、両方を1つのセットとして掴める
- **作業を畳める** — 開いたものだけを閉じる。デスクトップが前の作業を引きずらない
- **開く → 作業 → 畳む** が1周する。セッションという単位が初めて成立する

## User Personas

### Primary Persona: エンジニア（個人利用）
- **Demographics:** 25〜40歳、ソフトウェアエンジニア、Windows 11 デスクトップ
- **Goals:** 複数案件を並行し、1日に数回切り替える。切り替えのたびに前の作業の残骸を片付け、次の作業を立ち上げ直している
- **Pain Points:** グループを作るのが面倒で作らないまま。終業時にタブとウィンドウが30個残っている

## User Journey Maps

### Primary Journey: 気づいたときに保存する

1. **Awareness:** 案件Aの調査中。ブラウザに5タブ、Explorer に2フォルダが開いている。「この状態、また明日も作りたい」と気づく
2. **Consideration:** 今のグループ機能だと、7件を思い出して1件ずつ検索欄から足すことになる
3. **Adoption:** 拡張機能のアイコン（またはブラウザ側のホットキー）から「この作業を保存」。開いているタブと Explorer のウィンドウが一覧で出るので、不要な2件のチェックを外して名前を付ける
4. **Usage:** 翌朝、Groups ビューでそのカードを1クリック
5. **Retention:** 案件Bに移るとき、カードの「閉じる」で案件Aが開いたものだけが消える

### Secondary Journey: 終業

1. 19時、ブラウザに20タブ、Explorer に4ウィンドウ
2. 開いている各グループの「閉じる」を押す
3. 自分が後から開いた無関係なタブは残る（アプリが開いたものだけが対象）

## Feature Requirements

### Must Have Features

#### Feature 1: 作業状態のキャプチャ

- **User Story:** ユーザーとして、今開いているものをそのままグループにしたい。そうすれば、何を入れるべきか思い出さずに済む
- **Acceptance Criteria:**
  - [ ] Given ブラウザに複数タブと Explorer に複数フォルダが開いている, When 拡張機能から「Capture」を実行する, Then タブとフォルダの一覧が候補として提示される
  - [ ] Given 候補一覧が表示されている, When 不要な項目のチェックを外して名前を入力する, Then その項目を除いたグループが作成される
  - [ ] Given 候補に既存ブックマークと同じ URL / パスが含まれる, When 保存する, Then 新しいブックマークは作られず、既存のものがグループに追加される（重複を増やさない）
  - [ ] Given 候補に未登録の URL / パスが含まれる, When 保存する, Then ブックマークが新規作成され、タグルールによる自動タグ付けが適用される
  - [ ] Given Explorer が1つも開いていない, When キャプチャする, Then タブだけでグループが作られ、エラーにはならない
  - [ ] Given 拡張機能がアプリとペアリングされていない, When キャプチャしようとする, Then ペアリングを促し、勝手に失敗しない
  - [ ] Given アプリ本体からキャプチャを実行した, When 実行される, Then Explorer のウィンドウのみが対象になり、**ブラウザのタブは含まれないことが画面上で明示される**（後述の制約による）

#### Feature 2: グループを閉じる

- **User Story:** ユーザーとして、作業を終えるときに、その作業のために開いたものだけを閉じたい。そうすれば、次の作業に前の作業が混ざらない
- **Acceptance Criteria:**
  - [ ] Given グループを起動して作業している, When そのグループの「閉じる」を実行する, Then その起動で開いたタブと Explorer ウィンドウが閉じる
  - [ ] Given 起動後にユーザーが自分で別のタブを開いた, When グループを閉じる, Then **そのタブは閉じない**
  - [ ] Given グループが開いたタブで、ユーザーが別の URL に移動している, When グループを閉じる, Then **そのタブは閉じない**（作業中のものを奪わない）
  - [ ] Given ユーザーがすでに手で閉じたタブがある, When グループを閉じる, Then エラーにならず、残りが閉じる
  - [ ] Given グループを閉じようとしている, When 実行する, Then 閉じる対象の件数が提示され、確認を経てから閉じる
  - [ ] Given アプリを再起動した, When 前回の起動で開いたものを閉じようとする, Then 追跡情報が失われていることを伝え、何も閉じない（誤爆させない）

### Should Have Features

#### Feature 3: 中断メモ
- グループに「どこまでやったか」の1行を残せる。キャプチャ時と「閉じる」時に入力を促し、次に開いたときに表示する。既存の `memo` と同じ扱いで、グループ単位に持つ

#### Feature 4: 差分の取り込み
- 起動中のグループについて「今開いているものとの差分」を出し、増えた分をワンクリックでメンバーに追加する。キャプチャの日常運用版

### Could Have Features

#### Feature 5: 時間帯による並べ替え
- `open_count` / `last_opened_at` はすでにある。曜日と時刻を記録すれば「平日9時にいつも開くグループ」を設定なしで先頭に出せる。小さな `group_opens` テーブルの追加で足りる

#### Feature 6: 逆引き
- Explorer であるフォルダを開いた、またはあるタブを見たとき、それを含むグループをトレイから提示する

### Won't Have (This Phase)

- **グループごとのショートカットフォルダ**（後述の「検討して見送ったもの」参照）
- **AI による自動タグ付け・要約** — 競合が一様に実装済みでコモディティ化しており、差別化にならない
- **クラウド同期・アカウント** — 「アカウント不要・ローカル SQLite のみ」は現在の差別化要因そのものであり、これを壊す
- 他アプリケーション（エディタ、ターミナル）の起動状態のキャプチャ
- macOS / Linux 対応

## Detailed Feature Specifications

### アーキテクチャ上の制約: アプリは拡張機能を呼べない

**これが両機能の設計を決める最大の制約である。**

現在の通信は一方向で、拡張機能がクライアント、アプリ（`127.0.0.1:37373` の axum サーバー）がサーバーである。アプリ側から拡張機能に「今のタブを教えて」「このタブを閉じて」と要求する経路は存在しない。

取りうる選択肢は2つ。

| 方式 | 内容 | 評価 |
|------|------|------|
| **拡張機能を起点にする** | ユーザーが拡張機能側で操作する。拡張機能が `chrome.tabs.query` でタブを集め、37373 に POST する | **採用**。新しい通信経路が不要で、既存の設計と権限のまま成立する |
| アプリからのプッシュ | 拡張機能がポーリングするか、WebSocket / long-poll を張る | 見送り。常時接続かポーリングの運用コストが増え、サービスワーカーの停止と再開を扱う必要が出る |

拡張機能の `manifest.json` には **`tabs` 権限がすでにある**ため、タブの列挙に権限追加は不要。ブラウザ側のホットキーが要る場合は `commands` の追加のみ。

**帰結として、キャプチャとクローズはブラウザ側から起動する。** アプリ本体からも実行できるようにするが、その場合は Explorer のウィンドウしか見えない。この非対称は隠さず UI に明示する（Feature 1 の受け入れ条件に含めた）。

### Feature: キャプチャ

**Description:** 開いているタブとフォルダを候補として提示し、選んだものからグループを作る。

**User Flow:**
1. 拡張機能のアイコン（またはブラウザ側ホットキー）から「Capture」
2. 拡張機能が `chrome.tabs.query({ currentWindow: true })` でタブを集める
3. `POST /api/sessions/capture` にタブ一覧を送る
4. アプリ側が Explorer の開いているウィンドウのパスを集め、両者を1つの候補一覧にしてアプリのウィンドウを前面に出す
5. ユーザーがチェックを外し、名前を付けて保存
6. 未登録の URL / パスはブックマークとして新規作成し、既存のものは再利用してグループに追加

**Business Rules:**
- **既存ブックマークとの照合は必須。** 照合せずに作ると、キャプチャのたびに同じ URL のブックマークが増殖する。URL は正規化して比較し、パスは大文字小文字を無視して比較する（Windows）
- `chrome://`、`about:`、拡張機能自身のページは候補から除外する
- 新規作成されるブックマークにはタグルールを適用する（手動追加と同じ扱い）
- 候補が多いとき（20件以上）は全解除の導線を出す。20タブを黙って全部入れない

**Edge Cases:**
- 同じ URL のタブが複数開いている → 候補では1件にまとめる
- Explorer が「デスクトップ」や「PC」など実パスのない場所を開いている → 候補から除外する
- ネットワークドライブ、UNC パス → 候補に含めるが、存在確認はしない（オフラインでも保存はできてよい）
- 拡張機能が未ペアリング → ペアリング導線を出す

**判明した制約: エクスプローラーのタブは見えない**

`IShellWindows` が列挙するのは**ウィンドウ**であり、タブではない。3つのタブを持つ Windows 11 のウィンドウも1エントリで、`LocationURL` が返すのは**表示中のタブ**のフォルダだけ。残りは見えない。

これは `explorertabs` と同じ穴を反対側から見たものである。Windows はタブを作る手段を公開していないのと同じ理由で、タブを列挙する手段も公開していない。

**002 と組み合わせたときに一番効く。** 既定の `tabs` モードで3フォルダのグループを開くと1ウィンドウ3タブになり、それをキャプチャし直すと1フォルダしか出ない。塞ぐ手段はないので、キャプチャのダイアログに「各ウィンドウで表示中のタブだけが対象」と明示する。ユーザーが画面で見えているものより少なく返しておいて黙っている、という状態にはしない。

**技術的な要点:**
- Explorer のウィンドウのパス取得は `IShellWindows` を列挙し、各シェルウィンドウの `LocationURL` から得る。**002 でタブ生成に `IShellWindows` を使わなかったのとは事情が異なる**: あちらは「今開いたウィンドウを同定する」目的で `EnumWindows` の差分の方が確実だったが、こちらは「開いている全ウィンドウのパスを読む」目的であり、`LocationURL` はそのための公開された手段である
- `IWebBrowser2` の windows crate 上での所在は実装時に確認する。002 でこれを避けたのは不確実性のためであり、ここでも最初に潰すべき項目

### Feature: グループを閉じる

**Description:** そのグループの起動が開いたものだけを閉じる。

**Business Rules:**
- **自分が開いたものだけを閉じる。** これが守れなければ機能ごと出すべきではない。ユーザーが自分で開いた無関係なタブを1度でも巻き込めば、二度と使われない
- 判定は「起動時に記録した対象」と「今の状態」の両方を見る。タブ ID が一致し、**かつ URL が起動時のまま**であるものだけを閉じる。ユーザーがそのタブで別の作業を始めていたら対象外
- 追跡情報はアプリのメモリ上に持ち、DB には永続化しない。再起動後に古い情報で閉じるのは誤爆のリスクしかなく、その状況では「閉じられない」と伝える方が正しい
- 実行前に件数を提示して確認を取る

**Edge Cases:**
- 同じグループを2回起動した → 直近の起動を対象にする
- 閉じる対象のタブがブラウザの最後のタブ → ブラウザごと終了してしまうため、その1件は閉じずに残す
- Explorer ウィンドウがタブ化されている（002 の機能を使った）→ ウィンドウ単位で閉じることになり、そのウィンドウ内の他のタブも閉じる。**タブ単位で閉じる手段は Windows にないため、この挙動を確認ダイアログで明示する**
- ユーザーが起動後にそのウィンドウで別のフォルダに移動した → タブと同じ理由で対象外にする

## 検討して見送ったもの: グループごとのショートカットフォルダ

「グループを Explorer のサブフォルダとして出し、他アプリのファイルダイアログから届くようにする」案を検討した。**見送る。**

`src-tauri/src/shortcutdir.rs` はこれを既に検討し、意図的にフラット構成を選んでいる。モジュールの設計意図から:

> Deliberately **flat**: one bookmark, one shortcut, no per-tag subfolders. Tag subfolders would need name sanitizing, rename cascades and whole-folder deletes — the expensive and dangerous parts

タグをグループに置き換えても同じ問題が残る。名前のサニタイズ、リネームの伝播、そして**フォルダ単位の削除**。特に最後が重い。あのモジュールの安全性は「自分のマニフェストに記録したファイルだけを、それが管理下のディレクトリ直下にあり `.lnk` である場合にのみ削除する」という一点で成立している。ディレクトリの削除を導入すると、この保証を設計し直すことになる。

得られる価値（ファイルダイアログの中に作業セットが出る）は本物だが、**払うコストは「安い拡張」ではなく「安全性の再設計」である**。キャプチャとクローズを先に出し、必要性が実利用で確認できてから、ディレクトリ削除の安全性を単独の課題として扱う。

## Technical Design

### データモデル

キャプチャは既存のテーブルだけで足りる。`bookmarks` と `bookmark_groups` / `bookmark_group_items`（002 で追加）に書き込むだけで、新しいテーブルは不要。

クローズの追跡情報は**永続化しない**（前述）。`AppState` にメモリ上の記録を持つ:

```rust
/// 直近の起動が何を開いたか。再起動で失われてよい — 古い記録で閉じるのは
/// 誤爆のリスクしかない。
pub struct OpenedSession {
    group_id: String,
    /// (tab id, 起動時の URL)。URL が変わっていたら閉じない。
    tabs: Vec<(i64, String)>,
    /// 開いた Explorer ウィンドウ。
    windows: Vec<isize>,
    opened_at: String,
}
```

### 新しい HTTP エンドポイント（`src-tauri/src/server.rs`）

```
POST /api/sessions/capture   拡張機能が集めたタブを渡し、候補一覧の作成を依頼する
GET  /api/sessions/closable  閉じるべきタブ id を拡張機能に返す
POST /api/sessions/closed    実際に閉じた結果を報告する
```

拡張機能側からの操作という制約に従い、クローズも拡張機能が `GET /api/sessions/closable` を叩いて対象を受け取り、`chrome.tabs.remove` を実行する形になる。Explorer ウィンドウはアプリ側が `WM_CLOSE` で閉じる。

### 拡張機能（`extension/`）

- `manifest.json`: `tabs` は追加済み。ブラウザ側ホットキーを付けるなら `commands` を追加
- `background/service-worker.ts`: キャプチャとクローズのハンドラ
- `popup/Popup.tsx`: 「Capture」の導線

### フロントエンド

- `src/components/CaptureDialog.tsx` — 候補一覧、チェックボックス、名前入力
- `src/components/GroupCard.tsx` — 起動中のグループに「閉じる」を出す
- `src/hooks/useBookmarkGroups.ts` — `captureSession` / `closeSession`

## Implementation Phases

| Phase | 内容 | 完了条件 |
|-------|------|----------|
| ✅ **P1: Explorer の読み取り** | `IShellWindows` から開いているウィンドウのパスを取る。単独で検証可能 | 実機で開いているフォルダの一覧が取れる。**ここが最大の技術的不確実性なので最初に潰す** |
| ✅ **P2: キャプチャ（アプリ側のみ）** | Explorer のウィンドウだけからグループを作る。拡張機能に触らない | ブラウザ抜きでキャプチャが成立する |
| **P3: キャプチャ（拡張機能）** | タブの収集、`/api/sessions/capture`、候補ダイアログ | タブとフォルダを1つのグループとして保存できる |
| **P4: クローズ** | 起動の追跡、確認ダイアログ、タブとウィンドウを閉じる | 自分が開いたものだけが閉じる |
| **P5: 中断メモ** | Should Have | |

P2 を独立させているのは、**拡張機能に手を入れる前にキャプチャの価値を確かめるため**である。Explorer だけのキャプチャでも「フォルダ2つを保存」は成立する。

### P1 / P2 の実装記録

| 事前の不安 | 結果 |
|-----------|------|
| `IWebBrowser2` が windows crate のどこにあるか | `Win32::UI::Shell` にあり、**feature 追加は不要**だった（`IShellWindows` / `LocationURL` / `HWND` すべて同じ場所） |
| `cargo check --target x86_64-pc-windows-gnu` | 通過 |
| `file:` URL からパスへの変換 | 4件のユニットテストで検証（ローカル / パーセントエスケープを含む日本語 / UNC / 非 file URL の棄却） |
| キャプチャダイアログの描画 | ブラウザで描画して確認。長いパスの省略、日本語、UNC 表示すべて正常 |
| 実機での `IShellWindows` の挙動 | **未検証**。Windows 実機が必要 |

実装で決めたこと:

- **ブックマークの作成はフロント側で行う。** タグルールの適用（`getAutoTagNames`）がフロントにあるため、Rust 側に同じ判定を二重に持たせない
- **既存ブックマークとの照合は `findDuplicateBookmark` を再利用する。** パスの正規化（区切り文字、大文字小文字、末尾スラッシュ）が既に実装されている
- **候補が8件を超えるときは既定で全解除。** 20フォルダを黙って全選択したグループは、ユーザーが意図したものではない
- **同じフォルダを開いた2つのウィンドウは1件にまとめる。** キャプチャの対象はウィンドウではなく場所である

## Constraints and Assumptions

### Constraints

- **アプリから拡張機能を呼べない。** ブラウザに関わる操作はすべて拡張機能起点になる
- Explorer のウィンドウからタブ単位で閉じる手段が Windows にない。002 でタブ化した場合、クローズはウィンドウ単位になる
- テストフレームワークが未整備。検証は手動チェックリストに依存する
- `IWebBrowser2` の windows crate 上の扱いが未確認。P1 で最初に潰す

### Assumptions

- ユーザーは Chrome / Edge を主ブラウザとして使い、拡張機能をインストール済みである
- 拡張機能未導入のユーザーにも、Explorer だけのキャプチャ（P2）は価値がある
- 1回のキャプチャで拾う対象は通常 5〜15 件

## Risks and Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| ユーザーが自分で開いたタブを閉じてしまう | **Critical** | Medium | タブ id と起動時 URL の両方が一致するものだけを閉じる。追跡情報は永続化しない。実行前に件数を確認。1件でも誤爆が出たら機能を止める |
| キャプチャのたびに同じブックマークが増殖する | High | High | 既存ブックマークとの照合を必須要件にする（URL は正規化、パスは大文字小文字無視） |
| `IWebBrowser2` が windows crate 上で扱いづらい | Medium | Medium | P1 で単独に検証してから先へ進む。行き詰まったら P2 以降の設計を見直す判断点にする |
| 拡張機能未導入だと機能が成立しない | Medium | Medium | P2（Explorer のみのキャプチャ）を独立フェーズにし、拡張機能なしでも価値が出る形を先に作る |
| タブ化した Explorer をウィンドウごと閉じて、無関係なタブを巻き込む | High | Medium | 確認ダイアログでウィンドウ単位になることを明示する。タブ単位で閉じる手段は存在しない |
| 20タブを黙ってグループに入れてしまう | Medium | Medium | 候補は既定で全選択にせず、件数が多いときは全解除の導線を出す |

## Open Questions

1. キャプチャの候補を既定で全選択にするか、全解除にするか。全選択は速いが、20タブのときに事故る。件数で切り替えるのが妥当か実利用で判断する
2. 「閉じる」をグループカードのどこに置くか。起動ボタンと隣接させると誤爆する。起動中のグループにだけ出す案が有力
3. ブラウザ側ホットキーを持たせるか。`commands` の追加で可能だが、アプリ側のサモンショートカットとの整理が要る
