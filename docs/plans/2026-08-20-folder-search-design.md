# 設計: ブックマークしたフォルダの中まで検索する

- **日付**: 2026-08-20
- **ステータス**: Phase 1・2 実装済み / Phase 3 は設定UIのみ未着手

## 背景 / 目的

現在の検索はブックマーク自身（タイトル / URL / メモ）のみを対象としている。一方で本アプリは
`kind='path'` によって**ローカルのフォルダを一覧に載せられる**という、他のブックマーク管理ツールに
ない構造を既に持っている。

そこで検索の射程を **ブックマークしたフォルダの中身のファイル名** まで広げる。

狙いは速度ではなく **スコープの質**。

| | 索引範囲 | 問題 |
|---|---|---|
| Windows 検索 | OS が決めた場所 | 遅い・作業フォルダは索引対象外のことが多い |
| Everything | 全ドライブ | ノイズが多い |
| **本アプリ** | **ユーザーが自分で選んだ20〜30箇所** | 狭いから速く、狭いから当たる |

「あの見積書、たしか案件Bのフォルダのどこかに」を1回の入力で解決する。

## 重要な制約と決定

| 論点 | 決定 | 理由 |
|---|---|---|
| 検索対象 | **ファイル名・フォルダ名のみ**（中身の全文は対象外） | 規模が一段違う。まず名前で価値が出るかを確かめる |
| 索引の保存 | **保存しない**（DBもファイルも作らない） | 後述。本設計の中核 |
| 走査のタイミング | **検索されたときに、その場で** | 常に正しい結果が返る |
| 保持するデータ | **画面に出す一致分（上限50件）のみ** | 走査しながら照合し、外れたものは即座に捨てる |
| 既存の絞り込み | **一切変更しない** | `useBookmarkFiltering` の同期フィルタは0msのまま維持 |
| 結果の表示 | カード一覧の**下に別セクション** | 上に出すとカードが押し下げられ視線が飛ぶ |
| 途中打ち切り | **しない**（必ず全フォルダを見る） | 「出なかった＝無い」と信じられることが速度より重要 |
| Windows 検索への委譲 | **不採用** | 後述 |

### なぜ索引を保存しないのか

検討の過程で「SQLiteに索引を持つ」「専用DBファイルに分ける」「メモリに保持する」を順に検討したが、
いずれも**対策を積む必要がある設計**だった。対策が要るのは、そもそも持つべきでないものを持って
いるからである。

決め手は次の事実:

> **Windows は一度読んだフォルダの情報を既にメモリにキャッシュしている。**

自前のキャッシュは、OS が既にやっていることの再実装になる。しかも自前のキャッシュには
「いつ古くなるか」「いつ捨てるか」が付いて回るのに対し、OS のキャッシュはファイルの変更を
知っているため常に正しい。

保存しないことで、以下が**対策ではなく消滅**する。

- バックアップ（`export_data`）への混入
- `%APPDATA%` 経由での別PCへの同期
- メモリの肥大（上限・退避・解放の仕組みが不要）
- 索引の陳腐化（保存したファイルが検索に出ない / 消したファイルが出てくる）
- ブックマーク削除時の孤児レコード掃除

### なぜ Windows 検索に委譲しないのか

- `search-ms:` で Explorer に検索させる方式は、**結果が Explorer の窓に出る**ため、
  アプリ内に結果を統合できない。目指している体験にならない。
- Windows Search のインデックスを直接引く方式は、**ユーザーのフォルダが索引対象である保証がない**
  （既定でインデックスされるのはドキュメント/デスクトップ程度で、`D:\作業\` のような場所は通常対象外。
  ネットワークドライブも基本的に入らない）。環境によって当たったりはずれたりする検索は、
  原因が特定できないぶん最もたちが悪い。

## 動作

### 検索の2レーン

```
入力「見積」
  │
  ├─ レーン1: ブックマーク（既存・同期）
  │    useBookmarkFiltering の useMemo でメモリ上の配列を絞る
  │    → 1文字目から 0ms で反映。今回一切触らない
  │
  └─ レーン2: フォルダの中身（新規・非同期）
       2文字以上 → 150ms デバウンス → Rust に問い合わせ
       → 走査して一致分だけ返る → カード一覧の下に出現
```

体感は「**カードは即座に、フォルダの中身は打ち終わってから一拍おいて下から生えてくる**」。

### 表示

```
┌─ Bookmarks ───────────────┐
│ [□] 案件B 共有フォルダ     │
│ [□] 見積テンプレート.xlsx  │
└───────────────────────────┘

In your folders (12)
┌─ 案件B 共有フォルダ ──────┐
│ 見積書_最終.xlsx          │
│   \2026\08\  · 3日前      │
│ 見積根拠.docx             │
└───────────────────────────┘
```

- 由来のブックマークごとにグルーピング
- クリックで既存の `open_path` を呼ぶ。副操作として「フォルダを開く」
- 上限に達したフォルダは「多すぎて全部は見ていない」旨をセクションに明示する
  （黙って取りこぼすのが最も悪い）

### ちらつき対策

打鍵中に下のセクションが跳ねると、上のカードを読んでいる目が邪魔される。

- **前の結果を消さない** — 次が来るまで直前の結果を薄く残す。空にしてから埋めると点滅する
- **順序の逆転を捨てる** — リクエストに通し番号を持たせ、古い応答が後から届いたら破棄
- **進捗表示は300msを超えてから** — キャッシュを持たないため、その日はじめてのフォルダは
  数秒かかりうる。隠さず控えめに「フォルダを検索中…」を出す

## 走査の安全弁

ここが本機能の成否を分ける。

| 弁 | 既定値 | 理由 |
|---|---|---|
| 深さ上限 | 3 | 大半の作業フォルダはこれで覆える |
| 1フォルダあたりの件数上限 | 20,000 | 超えたら打ち切り、UIに明示 |
| 除外ディレクトリ名 | `node_modules` `.git` `target` `venv` `__pycache__` `dist` `obj` `bin` `.next` | **必須**。`node_modules` 一つで3万〜10万ファイルあり、これを踏むと上限をノイズだけで使い切る |
| reparse point | 辿らない | ジャンクション/シンボリックリンクは無限ループの温床 |
| 隠し・システム属性 | スキップ | ノイズ |
| ネットワーク/リムーバブル | 既定で対象外 | `GetDriveTypeW` で判定。明示的に有効化したときだけ走査 |
| 実行スレッド | 専用スレッド + `THREAD_MODE_BACKGROUND_BEGIN` | CPU と I/O の優先度を下げ、フォアグラウンドのアプリと競合させない |

## 速度（実測 / 2026-08-20）

`cargo test --lib folder_search::tests::benchmark -- --ignored --nocapture` で計測。
対象は `D:\my-app`（多数のプロジェクトを含む開発フォルダ）と `Documents`。

| 対象 | 設定 | 一度読んだ後 | その日はじめて |
|---|---|---|---|
| `D:\my-app` | 既定（深さ3・除外あり） | **6.8ms** | 1.71秒 |
| `D:\my-app` | 深さ5 | 21.8ms | 3.32秒 |
| `Documents` | 既定 | 0.28ms | 1.2ms |

**設計の中核だった賭けは実測で裏付けられた。** 温まった状態で 6.8ms ということは、
自前のキャッシュを作っても縮められるのは高々7ミリ秒であり、そのために陳腐化・肥大・
バックアップ混入の問題を抱え込む理由がない。OS のキャッシュが仕事をしている。

弱点も見積もり通り。**その日はじめてのフォルダは1.7秒**かかる。ここは進捗表示で隠さない。

深さ5は cold が倍・warm が3倍になり、増えたヒットは1件だった。**既定の深さ3は妥当。**

### 除外リストの効果（実測）

`D:\my-app` を深さ3で走査したときの訪問エントリ数:

| | エントリ数 | 時間（温まった状態） |
|---|---|---|
| 除外あり | **853** | 0.01秒 |
| 除外なし | 5,193 | 2.56秒 |

**6倍の差。**「除外リストは必須」という設計上の主張は実測で裏付けられた。

## 後から戻れる設計

実際に使って「その日の1回目の遅さが我慢ならない」となった場合は、キャッシュを追加すればよい。

**`search_in_folders(query, limit)` という入口を1つに保つ**ことで、中身をキャッシュ方式に
差し替えても外から見て何も変わらない追加変更で済む。逆順（先に作り込んでから削る）は捨てるのが大変。

## 実機で見つかった修正（2026-08-20）

ドライブ直下（`C:`）をブックマークした状態で検索すると、**一致が0件でも
「folder too large to search fully」が毎回表示された**。

原因は2つあり、どちらも設計判断の誤りだった。

1. **一致0件でも `truncated` なら結果に含めていた。**「黙って取りこぼさない」という
   意図自体は正しいが、置き場所を誤った。**「このフォルダは大きすぎる」はクエリに
   依存しない情報**であり、検索結果として並べるものではない。毎回同じ行が出続けると、
   セクション全体を無視する訓練になる。
2. **ドライブ直下を走査対象にしていた。**ドライブ全体は「ユーザーが選んだ意味のある場所」
   ではなく、この機能が避けると宣言したもの（Everything 的な全走査）そのもの。
   しかも毎クエリ2万件を無駄に走査して何も返していなかった。

修正:

- ドライブ直下は走査せず `drive-root` としてスキップ扱いにする（`is_drive_root`）
- 一致0件のグループはUIに出さない
- 不完全さの注記（drive-root / network / removable / too large）は、
  **結果が1件以上あるときだけ**下部に小さくまとめて出す。単独では出さない
- 一致があるフォルダが打ち切られた場合のみ、そのグループに「more may exist」を出す


## 上限の見直し（2026-08-20）

実測にもとづき、3つの上限をそれぞれ別の性質のものとして整理した。

| 上限 | 値 | 性質 | 判断 |
|---|---|---|---|
| 深さ | 3 | **本当の制限。**エントリ数を決めているのはこれ。温かいときはほぼ無料だが、冷たいときのコストが倍になる（深さ3で1.71秒 → 深さ5で3.32秒、増えたヒットは1件） | 据え置き。Phase 3 で設定可能にし、実使用で決める |
| 件数 | 20,000 | **防護柵。**実フォルダは除外リスト込みでツリー全体でも約3,000件と、上限の7分の1にも届かない | 据え置き。引き上げても実害も実利もない |
| 保持件数 | 20 → **200** | **走査コストと無関係。**一致件数に関わらず走査量は同じで、増えるのは JSON サイズと描画のみ | **引き上げた**（下記） |

### 保持件数を 20 → 200 に引き上げた理由

20件のままだと「showing 20 of 47」と表示しながら**残り27件を見る手段がない行き止まり**になっていた。
単に数字を増やしても上限の位置が動くだけで行き止まりは消えないため、UI 側に展開を用意した。

- Rust は最大200件までグループに保持する（走査コストは不変）
- UI は最初20件だけ描画し、`Show N more` で展開・`Show fewer` で畳む
- 検索語が変わったら展開状態はリセットする（下の行は別のファイルになるため）
- 200件も超えた場合は展開しても届かないので、
  `showing 200 of 1,240 — narrow your search` と正直に出し、展開は提示しない

この機能で探すのは「名前をうろ覚えのファイル」なので、「もっと絞ってください」だけでは
詰む場面がある。一覧を眺めて気づく経路を残す必要がある、という判断。

### 走査順を深さ優先から幅優先に変更

件数上限に達したとき、深さ優先だと**予算が1つの深いサブツリーに吸い込まれ、隣のフォルダを
一度も開かないまま終わる**。どのファイルが見つかるかがファイルシステムの返す順序次第になり、
ユーザーから見て理由も再現性もない。

幅優先にして、浅い階層から予算を使うようにした。人が探すものは浅いところにある。
深さ優先だと失敗するテスト `spends_a_tight_budget_on_shallow_entries_first` を追加。

### 上限到達時の実測

25,000ファイル（20,000で打ち切り）: 温かいとき **48ms** / 冷たいとき 218ms。
上限いっぱいまで走っても十分速く、20,000という値には余裕がある。


## ブックマーク一覧との統合（2026-08-20）

結果セクションを「別物」ではなく**一覧の続き**として扱うようにした。

### 列数の共有

列クラスの対応表を `src/lib/listLayout.ts` に切り出し、`BookmarkList` と
`FolderSearchResults` の両方が同じものを使う。片方だけ列数が変わって
同じ画面の上下で違うグリッドになる、という事故を構造的に防ぐ。

### キーボード操作の対象に含める

`useBookmarkTabNavigation` と `useBookmarkArrowNavigation` は
`document.querySelectorAll("[data-bookmark-card-link]")` で対象を集める作りなので、
結果の行に同じ属性を付けるだけで **Tab / Shift+Tab / 矢印4方向 / Home / End が
すべてそのまま効く**。フック側の変更は不要だった。

- 行の外側 `div` に `data-bookmark-id`（値はフルパス）
  — 矢印の上下移動がグリッドセルの座標を測るのに使う
  （`useBookmarks.ts:128` の `[data-bookmark-id="<uuid>"]` 検索とは値が衝突しない）
- 開くボタンに `data-bookmark-card-link`
- カードと同じ `focus-within` のリングを付け、フォーカス位置が見えるようにした

DOM 上で結果セクションはカードの後ろにあるため、Tab も矢印も
カード → 結果の行、と自然に流れる。

### 既知の制約

Tab は `[data-bookmark-card-link]` の間だけを回る設計なので、
行内の「親フォルダを開く」ボタンと「Show N more」はキーボードで到達できない。
これは既存のカード内アクションボタンと同じ扱いであり、この機能だけ例外を作ると
かえって一貫性を欠くため、現状は揃えている。


## 除外ルールの通知をやめた（2026-08-21）

`Not fully searched: C: (drive root)` のような、**除外ルールに基づくスキップの通知を
UI から外した**。ヘルプの「フォルダの中も検索」に除外対象を明記したため。

判断の軸は一貫していて、**恒久的で予測できる事実は、毎回の検索結果に出さない**。
ドライブ直下・ネットワーク・リムーバブルは、ブックマークの性質として常に対象外であり、
何を打っても同じ行が出る。これはこの機能で3度目の「全行に同じものが並ぶ」問題だった。

一方 **「大きすぎて全部見られなかった」は残した。**これは除外ルールではなく実行結果で、
自分のフォルダが2万件を超えているかはヘルプを読んでも予測できない。起きたときにだけ
`Too large to search fully: …` と出す。

`search_in_folders` は `skipped` を返し続ける（UI は読まない）。Phase 3 の設定画面で
「このブックマークは検索対象外（ドライブ直下のため）」を出すのに使える情報であり、
捨てるより持っておくほうが素直なため。
