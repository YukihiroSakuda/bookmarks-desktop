# 設計: Everything との差を埋める — 検索構文・ランキング・先読み

- **日付**: 2026-09-02
- **ステータス**: 一部実装 — 機能Aのうち「複数語 AND」と引用符は 2026-11-19 に実装（`src/lib/searchQuery.ts`、Rust 側は `split_search_terms` / `build_terms`）。`search_in_folders` の引数は `query_forms` から語ごとの `query_terms: string[][]` に変わった。`ext:` などの演算子・機能B・機能Cは未着手
- **前提**: [2026-08-20-folder-search-design.md](2026-08-20-folder-search-design.md) の Phase 1・2 実装済み

## 背景 / 目的

フォルダ内検索は動いている。しかし「ファイル名で探す」という一点においては、
Everything（voidtools）が事実上の基準であり、ユーザーは無意識にそれと比べる。

本設計は **Everything との差を全部埋めることを目的にしない。**
差を「本物の差」と「意図的に作った差」に仕分け、前者だけを埋める。

## 差の棚卸し

前設計の実測値（`D:\my-app`・深さ3・除外あり）を根拠に判定する。

| 論点 | Everything | 本アプリ | 判定 |
|---|---|---|---|
| 索引範囲 | 全ドライブ（MFT） | ブックマークした20〜30箇所 | **意図的な差。埋めない** |
| 深さ | 無制限 | 3 | **差ではない**（後述） |
| 応答（温まった後） | 瞬時 | 6.8ms | **差ではない** |
| 応答（その日はじめて） | 瞬時 | **1.71秒** | ○ 本物 |
| クエリ構文 | `ext:` `dm:` `size:` ワイルドカード `!` | 部分一致のみ | ○ **最大の差** |
| 結果の並び | 名前/日付/サイズ/パスで並べ替え可 | 走査順のまま・200件で打ち切り | ○ 本物（かつ取りこぼす） |
| 複数語 | 空白区切りで AND | **できない** | ○ 本物 |
| 全文検索 | 1.5 で対応（低速・任意） | なし | 範囲外（後述） |
| ローマ字/かな | なし | **対応済み** | ← こちらが勝っている |

### 埋めない差:索引範囲

前設計の中核的主張であり、覆す理由がない。むしろ**製品の主張そのもの**である。

> 狭いから速く、狭いから当たる

全ドライブを索引すると `AppData` と `Program Files` のノイズを相手にすることになり、
「自分で選んだ場所だけ」という価値が消える。Everything が既に無料で存在する以上、
劣化版の Everything を内蔵しても誰も使わない。

加えて、MFT を直接読む方式は **ボリュームハンドルに管理者権限を要求する**
（Everything が常駐サービスを持つのはこのため）。MSIX/Store 版は `runFullTrust` のみで
昇格できないため、**Store 版だけ検索が動かない**という最悪の分岐を抱え込む。

### 埋めない差:深さと「温まった後の速度」

どちらも**実測が「差ではない」と言っている。**

| 実測 | 結果 |
|---|---|
| 深さ5に変更 | cold 2倍・warm 3倍のコストで、増えたヒットは **1件** |
| 温まった状態の走査 | **6.8ms** |

6.8ms ということは、索引を自前で持っても**縮められるのは高々7ミリ秒**である。
その7ミリ秒のために、陳腐化・肥大・バックアップ混入・削除時の孤児掃除を抱え込む取引は成立しない。

### 範囲外:全文検索

規模が一段違う（docx/xlsx/pdf のパーサが必要）。前設計の
「まず名前で価値が出るかを確かめる」という段取りを維持する。名前検索の構文が整い、
それでも足りないと分かってから着手する。

## 埋める差 — 3つの機能

### 機能A. クエリ構文（最優先）

Everything の構文のうち、**この製品の用途で効くものだけ**を採る。

| 構文 | 例 | 実装コスト | 備考 |
|---|---|---|---|
| 複数語 AND | `見積 2026` | 小 | 現状 `contains` 1回のため「見積 2026」は0件になる。**最も安く最も効く** |
| `ext:` | `ext:xlsx` `ext:xlsx;docx` | 小 | 「あのExcel」に直撃 |
| `!` 除外 | `見積 !旧` | 小 | ノイズ潰し |
| `dm:` | `dm:today` `dm:thisweek` `dm:>2026-08-01` | 中 | `modified_at` は既に読んでいる |
| `file:` / `folder:` | `folder:案件` | 小 | `is_dir` は既に判っている |
| `size:` | `size:>10mb` | 小 | 文書用途では優先度低。同時に入れるなら入れる程度 |
| ワイルドカード `*` | `見積*最終` | 中 | **見送り**。複数語 AND がほぼ代替する |

**引用符** `"..."` は空白を含む語のために必要。

#### パースはフロント側で行う

ローマ字/かな展開（`buildQueryForms`）は既に
`src/lib/searchNormalize.ts` にあり、フロントで走っている。
**演算子はかな展開してはいけない**（`ext:` を平仮名化しても意味がない）ので、
語と演算子の分離はかな展開の**手前**に置く必要がある。したがってパーサはフロント側。

Rust に渡す形は、現在の `query_forms: Vec<String>` を構造体に置き換える:

```
{
  terms:    [ { forms: ["見積"], negated: false },
              { forms: ["2026"], negated: false } ],
  ext:      ["xlsx"],
  kind:     "file" | "folder" | null,
  modified: { op: ">", epochMs: … } | null,
  size:     { op: ">", bytes: … } | null
}
```

前設計の「**`search_in_folders` という入口を1つに保つ**」方針は維持する。
コマンド名も戻り値の形も変えず、引数の中身だけが richer になる。

#### 構文を覚えなくても使えること

構文はパワーユーザ向けの上乗せであり、**知らない人の体験を1ミリも劣化させてはいけない。**

- `:` を含まない入力は、今までどおり全体が1つの語として扱われる
- 未知の接頭辞（`foo:bar`）は**演算子と解釈せず、ただの語として扱う**
  （`http://` を含むファイル名で誤爆しないため）
- 検索欄の脇に小さく `?` を置き、押すと構文の早見表を出す

### 機能B. 結果のランキング

現状 `matches` は**走査順**（幅優先）で積まれ、`max_matches_per_group: 200` を超えたら
以降は捨てられる。つまり **201番目に走査された正解は、画面に出ない。**
ヒット数だけは正しく表示されるので、「12件あると言っているのに目的のものが無い」が起きる。

これは Everything との差である以前に**バグに近い挙動**であり、機能Aで複数語 AND が入って
ヒット数が減る前に直しておきたい。

#### スコア

| 要素 | 重み | 理由 |
|---|---|---|
| 拡張子を除いた名前が完全一致 | 最大 | `見積書.xlsx` を `見積書` で引いたとき |
| 先頭一致 | 大 | |
| 語境界での一致（`_` `-` ` ` `.` の直後） | 中 | `2026_見積書` が `見積` で当たる |
| 単なる部分一致 | 小 | |
| 全語が近接している | 小 | 複数語 AND のとき |
| 浅い（`relPath` の区切り数が少ない） | 小 | ルート直下ほど本命 |
| 更新が新しい | 極小 | 同点の決着用 |

**打ち切りは「先着200件」から「上位200件」に変える。**
実装は容量200の min-heap で足りるため、メモリ上限は現状と変わらない。

並べ替えの UI 露出（名前順/日付順に切り替え）は**今回は入れない**。
まず既定の順序を賢くする。切り替えが要るかは使ってから決める。

### 機能C. コールドスタートの先読み

唯一残る、本物の速度差。**その日はじめてのフォルダは1.71秒。**

ここで自前の索引に手を出さないことが重要である。前設計の観察はこうだった:

> Windows は一度読んだフォルダの情報を既にメモリにキャッシュしている。
> OS のキャッシュが仕事をしている。

**ならば、そのキャッシュを「ユーザーが打ち始める前」に温めればよい。**
自前のキャッシュを持つのではなく、OS のキャッシュを先に働かせる。

- アプリ起動から一定時間後、`last_accessed_at` 上位 **5件** のフォルダを走査する
- **結果は全部捨てる。** 何も保持しない。目的は副作用（OS キャッシュの充填）だけ
- 既存の `enter_background_priority()` をそのまま使う（CPU・I/O 優先度を下げる）
- 本物の検索が始まったら即座に中断する（`SEARCH_GENERATION` を流用）

保持するものがゼロなので、前設計が索引を却下した理由
（陳腐化・肥大・バックアップ混入・孤児掃除）に**一つも触れない。**

#### これは仮説である

「走査すれば OS キャッシュが温まり、その効果が数分から数十分持続する」は
**まだ測っていない仮説**である。OS はメモリ圧で随時追い出すため、
効果が5分で消えるなら機能として成立しない。

したがって **実装前に計測する**:

1. フォルダを走査 → 待機 → 再走査、を待機時間 1/5/15/30/60分 で測る
2. 30分後も warm 水準（10ms 台）を保つなら採用
3. 数分で cold に戻るなら **本機能は破棄**し、1.71秒は進捗表示で正直に見せ続ける

破棄が正しい結論になりうる、という前提で着手する。

#### 起動直後に走らせない

自動起動（`--hidden`）はログイン直後であり、Windows が最も混んでいる瞬間である。
そこに走査を足すのは体感の悪化にしかならない。**起動から60秒後**に開始する。

## 触らないもの

| | 理由 |
|---|---|
| `useBookmarkFiltering` の同期フィルタ | 前設計から続く方針。カードは0msのまま |
| 深さ3・20,000件・除外リスト | 実測で妥当と確認済み |
| 索引・キャッシュの保存 | 本設計の結論。README とプライバシーの記述も変えない |
| ネットワーク/リムーバブルの既定除外 | 変えない |
| 全文検索 | 範囲外 |

**DB のスキーマ変更・マイグレーションは無い。保存するものも無い。**
（機能Aの構文ヘルプを Settings に出す場合のみ `settingsText.ts` に追記が要る）

## 見送った案

| 案 | 却下理由 |
|---|---|
| MFT + USN ジャーナルで全ドライブ索引 | 管理者権限が要る → **MSIX/Store 版で動かない**。かつ製品の主張と逆行 |
| `ReadDirectoryChangesW` でメモリ内索引 | 昇格は不要だが、warm 6.8ms を縮めるためだけに陳腐化と肥大を抱える。**割に合わない** |
| 深さ上限の引き上げ | 実測で+1件。コストは cold 2倍 |
| Windows Search への委譲 | 前設計で却下済み（ユーザーのフォルダが索引対象である保証がない） |
| 正規表現 | 構文の複雑さに対して用途が狭い。複数語 AND で足りる |
| 並べ替え UI | まず既定の順序を賢くする。必要性は使ってから判断 |

## 判断の要点

**Everything に勝てる土俵は「範囲」ではなく「絞り込みの表現力」である。**

全ドライブに対する `ext:xlsx dm:thisweek 見積` は候補が多すぎて実用にならないが、
**自分で選んだ20〜30箇所**に対する同じクエリは、ほぼ一意に当たる。
狭いスコープは構文と組み合わせたとき初めて完全な武器になる。

機能Aは、既に持っている「狭さ」の価値を倍にする機能であり、
Everything の模倣ではない。
