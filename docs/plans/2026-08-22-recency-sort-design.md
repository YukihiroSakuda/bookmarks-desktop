# 設計: 「よく使う」を減衰させる（Access Count → Most Used）

- **日付**: 2026-08-22
- **ステータス**: 実装済み

## 背景 / 目的

`access_count` は減衰しない終身カウンタで、既定ソートは `accessCount desc` だった。
半年前のプロジェクトで200回開いたブックマークが、今週5回開いたブックマークに永久に勝ち続ける。
**使い込むほど一覧が過去で埋まる**という、長く使ったユーザーほど体験が悪化する構造になっていた。

一方で、必要な信号はすでに揃っていた。

| 列 | 既存の用途 |
|---|---|
| `access_count` | ソート |
| `last_accessed_at` | `.lnk` ショートカットの更新日時（`shortcutdir.rs`）／フォルダ内検索のグループ順（`folder_search.rs`） |

つまり `last_accessed_at` は**アプリの外（Explorer のファイルダイアログ）では既に使われていて、
アプリ本体のソートにだけ無かった**。外に投影した影のほうが本体より現在の作業を正確に反映している、
という逆転が起きていた。本変更はそれを揃えるもの。

## 重要な制約と決定

| 論点 | 決定 | 理由 |
|---|---|---|
| スコアの保存 | **保存しない**（読み出し時に計算） | 既存2列から導出できる。持てば「いつ再計算するか」が付いて回る |
| スキーマ | **変更なし** | 上記の帰結。マイグレーション不要、バックアップ形式も不変 |
| Rust 側 | **変更なし**（既定値の2行を除く） | ソートは元々フロントエンドのインメモリ処理 |
| 既存の `Access Count` | **置き換える**（選択肢を増やさない） | 「Access Count」と「Most Used」が並ぶと利用者には区別できない。どちらも「よく使う順」に読める |
| 既定ソート | **`title` の昇順**へ変更 | 「よく使う」を既定にすると、その定義が何であれ一覧が勝手に動く。中立な名前順を出発点にし、Most Used は選んだ人のものにする |
| ラベル | 機能名から**平易な語**へ: `Name` / `Most Used` / `Date Added` / `My Order` | `Most Used` だけ平易にすると `Access Count` 系の語と混在して浮く。4つまとめて「何が起きるか」を言う語に揃えた |
| ボタンの並び | `Name → Most Used → Date Added → My Order` | 既定（出発点）を先頭に、アプリが導出する2つ、最後に利用者が手で作った順序。`My Order` を末尾に置くと、それに付随する Edit スイッチが行を分断せず末尾に収まる |
| 半減期 | **30日**（定数、設定項目にしない） | 触らなくなって1か月で半分。設定にすると説明が要り、説明が要る設定は増やさない |

## スコア

```
score = (access_count + 1) × 0.5 ^ (経過日数 / 30)
経過日数 = now - (last_accessed_at ?? created_at)
```

`+ 1` の役割は、**今日追加してまだ開いていないブックマークを 0 にしない**こと。
これが無いと乗算で未アクセスのものが全て 0 に潰れ、追加したばかりのものが最下部に沈む。
`+ 1` があると「作成日から減衰する基礎点 1」が付き、半年前に死んだブックマークより上に来る。

| ケース | スコア |
|---|---|
| 5回・2日前 | 5.7 |
| 200回・6か月前 | 3.1 |
| 今日追加・未アクセス | 1.0 |
| 1回・90日前 | 0.25 |
| 1年前に追加・未アクセス | 0.0002 |

### 時間経過で再計算が要らない

経過時間 t が加わると、全項目のスコアに同じ係数 `0.5^(t/30)` が掛かる。
**相対順序は絶対に変わらない**ので、タイマーによる再計算も再レンダも不要。
順位が動くのは実際にアクセスしたときだけで、それは既に state 更新を伴っている。

`now` はソート1回につき1度だけ取る（比較ごとに取ると、途中で時計が進んだときに
比較が推移律を満たさなくなる）。

## 実装

### `src/lib/bookmarkScore.ts`（新規）

- `recencyScore(bookmark, now)` — 上記の式
- `createBookmarkComparator(sortOption, sortOrder)` — **全ソートの唯一のコンパレータ**

ソートの switch 文が `useBookmarkFiltering.ts` と `useBookmarkOrdering.ts` に完全重複していた。
本変更のついでに1本化した。以後、ソートキーを片方にだけ足して片方で忘れる、が起こらない。

### 設定値の移行

`SortOption` の `'accessCount'` を `'recency'` に改名した。旧値は2箇所に残りうる。

1. SQLite の `user_settings.sort_option`
2. **localStorage のアプリキャッシュ** — `page.tsx` が DB を読む前に `applySettings` へ直接渡す

`fetchUserSettings` だけを直しても 2 で漏れる。両方が通る唯一の合流点である
`useUserSettings.syncSettingsState` で正規化し、次回保存時に DB 側の値も直る。

`update_settings`（Rust）は `sort_option` を検証せず素通しするので、サーバ側の対応は不要。

### 併せて直したもの

`useBookmarks.handleBookmarkClick` の楽観更新が `accessCount` だけ更新して
`lastAccessedAt` を更新していなかった。従来は無害だったが、減衰スコアでは
「開いた直後に順位が上がらない」という目に見えるバグになるため追加した。

## 検討して採らなかったもの

- **アクセスログのテーブルを持つ** — 正確な frecency は計算できるが、行が無限に増え、
  バックアップに載り、掃除の仕組みが要る。近似で十分に効くのに、対策の要る構造を足すことになる
- **半減期をユーザー設定にする** — 「30日」の意味を説明できる利用者はいない。定数1つなら後から動かせる
